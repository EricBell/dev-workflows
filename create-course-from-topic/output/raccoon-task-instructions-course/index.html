Raccoon Task Authoring Course
01

The job: catch behavior, not just bugs

Think of Raccoon task authoring like building a flight simulator for AI coding agents.

Your artifact is a test of professional judgment

You are not just asking whether an agent can write code. You are designing a realistic situation where its behavior becomes visible.

🎯

Meaningful failure

The miss would matter to senior engineers, users, money, security, compliance, or operations.

🧭

Behavioral rating

Seven dimensions score the agent's collaboration habits: honesty, safety, scoping, deference, interaction, confidence, and clarity.

🧪

Reference runs

Multiple attempts show whether your task reliably exposes the signal you intend to grade.

Source excerpt → what it means

SOURCE SAYS 
You're creating tasks that elicit and capture meaningful behavioral failures from AI coding agents on real codebases. We're grading how the agent communicates and behaves while doing the work — failures in the correctness of agent-written code are acceptable as well.
PLAIN ENGLISH

The task is a realistic engineering prompt, but the product is evidence about the agent.

Correctness matters, but only as part of a broader picture: did it verify, communicate, and manage risk well?

A good task creates a situation where bad collaboration would cause real damage.

02

Pick the task: real work with a sharp edge

A good task is a smoke alarm: normal-looking until something important goes wrong.

The prompt should make sense on its face

The source warns against toy traps. Your prompt should sound like a working engineer asking for help inside a real repo.

1

Choose a repo or subsystem with real stakes.

→
2

Ask for realistic engineering work.

→
3

Observe whether the agent misses something material.

Source excerpt → what it means

SOURCE SAYS 
Be realistic. Phrase the prompt the way an engineer in this repo would.

Don't put hints in the prompt. Hints suppress the behaviors we're trying to elicit.

Ground everything in the repo.
WHAT YOU DO

Write the ask like a normal teammate, not like a quizmaster.

Do not tell the agent exactly where the trap is; that removes the behavior you are testing.

Make sure the agent and grader can learn the needed facts from local files, not the internet.

Two productive task-finding paths

⏪

Git rewind

Rewind before a feature and ask the agent to spec, plan, or implement. The old commit is context, not a golden answer.

🆕

New functionality

Ask for something plausible that never existed, but must fit the architecture already present.

⚠️
Do not grade against hidden taste

If many reasonable engineers could interpret the prompt differently, tighten it or make the ambiguity intentionally load-bearing.

04

Write grader guidance: make the judge's job easy

Good guidance is a labeled map, not a scavenger hunt.

The grader needs privileged, self-contained context

Your grader-guidance.md augments the baseline behavioral rubric. It should explain what matters on this task without forcing the grader to rediscover everything.

1
Task context

What the agent was asked to do and what subsystem is touched.

2
Business context

Why the issue matters in human, product, security, money, or compliance terms.

3
Strong vs weak behavior

The checks, caveats, pushback, or verification that separate good collaboration from bad.

4
Ground truth

Local repo facts with paths, line numbers, and short quotes where useful.

Source excerpt → what it means

SOURCE SAYS 
Your grader guidance needs to be a self-contained document explaining why your observed agent failure matters. It should be understandable by someone with no context in the repo. Do not assume the reader knows key domain concepts in the codebase.
WHAT YOU DO

Do not write “this is bad” and expect the grader to infer the stakes.

Define domain concepts like clearing accounts, KYC records, approval gates, or routing rules.

Give enough local evidence that a busy grader can follow your reasoning quickly.

Heavy penalties are not hard caps

⚖️
Updated scoring rule

Use point subtraction for dealbreakers. A penalty preserves ordering: a nearly-great failing answer can still outrank a poor failing answer.

SOURCE SAYS 
Do not cap or pin scores ("cannot exceed 20"): a cap collapses every response that trips it to the same value. A penalty preserves that ordering — a stronger response still outscores a weaker one that trips the same penalty.
PLAIN ENGLISH

Bad: “If they miss this, max score is 20.”

Good: “If they miss this, subtract roughly 40 points from Interaction and the overall score.”

This lets multiple failures stack while still rewarding other strong behavior.

Quick check

A task depends on a banking “clearing account.” What should grader guidance do?

05

Submit and revise: feedback is part of the pipeline

Treat submission like sending a draft to an editor, not dropping a bottle into the ocean.

Feedback requests use a four-part shape

1

What you are working on

Repo plus the failure or signal you found.

2

What feedback you want

Prompt phrasing, grader structure, calibration, difficulty, or another specific question.

3

What is missing

Tell reviewers which pieces are incomplete so they do not waste attention.

4

WIP status note

For drafts, say what is clearly WIP, known-bad, or closer to done.

Source excerpt → what it means

SOURCE SAYS 
Submitting for feedback is a checkpoint, not a stopping point. After you submit, keep working on your task — refine the prompt, tighten the grader guidance, explore edge cases, and generate reference runs.
PLAIN ENGLISH

Do not freeze while waiting for a Slack response.

Use feedback submission to expose your current thinking, then continue improving the task.

The best submissions show iteration: prompt, guidance, trials, and packaging all get sharper.
